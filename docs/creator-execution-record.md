# Creator Execution Record v1

## Purpose

Creator Execution Record records whether a user actually used a generated Creator Execution Pack and how far production progressed. It closes the local workflow without generating media or changing the upstream analysis:

```text
Creator Report
-> Creator Strategy Plan
-> user selects one topic
-> Creator Execution Pack
-> user clicks Start execution
-> Creator Execution Record
```

Record creation is always explicit. Generating or viewing an Execution Pack never creates a Record automatically.

## Relationship to Execution Pack

The Record consumes the existing validated `creator_execution_pack.json`. At creation time, the server copies these immutable identity fields from that Pack:

- `project_id`
- `execution_pack_generated_at`
- `execution_pack_topic_index`
- `selected_topic`

If the Execution Pack is regenerated later, the existing Record remains bound to the original values. One Record is current per Creator iteration; closed iterations remain available through Creator Iteration History.

## Schema

`CreatorExecutionRecordV1` uses version `1.0`:

```json
{
  "version": "1.0",
  "project_id": "clone_example",
  "execution_pack_generated_at": "2026-08-09T10:00:00+00:00",
  "execution_pack_topic_index": 0,
  "selected_topic": "同一妆造三种人物状态测试",
  "status": "in_progress",
  "production_status": {
    "shooting": "completed",
    "editing": "pending",
    "publishing": "pending"
  },
  "feedback": {
    "was_used": true,
    "difficulty": "normal",
    "quality_rating": 4,
    "result_rating": null,
    "notes": "拍摄已完成，等待剪辑。"
  },
  "created_at": "2026-08-09T10:05:00+00:00",
  "updated_at": "2026-08-09T10:08:00+00:00"
}
```

Top-level `status` is restricted to:

- `draft`
- `in_progress`
- `completed`
- `archived`

Each production stage is restricted to:

- `pending`
- `completed`
- `skipped`

## Lifecycle

1. Start creates a Record with `status=draft`, all stages `pending`, and `feedback.was_used=false`.
2. The first stage changed to `completed` or `skipped` changes a draft Record to `in_progress` and sets `was_used=true`.
3. When shooting, editing, and publishing are all `completed` or `skipped`, the Record becomes `completed`.
4. Feedback can be updated at any point. Ratings are optional.
5. An archived Record remains archived during automatic state derivation and feedback updates.

The lifecycle is intentionally small. There is no queue, retry state, workflow engine, polling loop, or background worker.

## API

### Start

```text
POST /api/creator-intelligence/projects/{project_id}/execution-record/start
```

The current Execution Pack must already exist and validate. Missing Packs return `EXECUTION_PACK_NOT_READY`. Start is idempotent: if the Record already exists, the same Record is returned and no second object is created.

### Get

```text
GET /api/creator-intelligence/projects/{project_id}/execution-record
```

Missing Records return `EXECUTION_RECORD_NOT_READY`.

### Partial update

```text
PATCH /api/creator-intelligence/projects/{project_id}/execution-record
```

Example:

```json
{
  "production_status": {
    "shooting": "completed"
  }
}
```

Nested production and feedback objects are merged. Fields omitted by the client are preserved. The client may update only:

- `status`
- `production_status.shooting`
- `production_status.editing`
- `production_status.publishing`
- `feedback.was_used`
- `feedback.difficulty`
- `feedback.quality_rating`
- `feedback.result_rating`
- `feedback.notes`

All identity fields and timestamps remain server-owned. `updated_at` is generated by the server for each successful PATCH.

All successful Record responses use `Cache-Control: no-store`.

## Feedback semantics

`difficulty` accepts an empty value, `easy`, `normal`, or `hard`. Quality and result ratings accept `null` or an integer from 1 through 5. A user can therefore record production progress before a video is published and add the result rating later. Notes are limited to 1000 characters.

## Persistence

Without an iteration index, the Record remains beside the existing Creator artifacts:

```text
outputs/creator_clones/{project_id}/creator_execution_record.json
```

After the user starts a new iteration, the current Record is stored at:

```text
outputs/creator_clones/{project_id}/iterations/{iteration_id}/creator_execution_record.json
```

Writes use a UTF-8 temporary file in the same directory, followed by `flush`, `fsync`, and `os.replace`. Updating a Record atomically replaces only that file. It does not modify:

- `creator_execution_pack.json`
- `creator_strategy_plan.json`
- `creator_clone_result.json`
- `samples.json`

## UI

The current Execution Pack panel reveals `开始执行` only after a Pack is available. Starting creates the Record synchronously and shows one compact status card with:

- shooting, editing, and publishing progress;
- complete and skip actions for each stage;
- optional usage, difficulty, quality, result, and note feedback;
- an archive action.

The UI does not poll and does not use a Job. Existing Records are loaded when their Execution Pack is restored. Desktop uses a compact three-column stage row; the 720 px breakpoint stacks stages and feedback fields for mobile.

## Security

Record APIs accept only local requests under the existing application guard. Server-owned identity fields are ignored when supplied by a client. Persisted Records and API responses redact:

- Cookie and known login-state assignments;
- Authorization and Bearer values;
- OpenAI-style API keys;
- HTTP(S) and signed media URLs;
- local absolute paths.

The Record never stores request headers, provider responses, credentials, or upstream bodies.

## Non-goals

Creator Execution Record v1 does not:

- generate video, images, speech, subtitles, or edits;
- publish content;
- search trends or hashtags;
- retrieve growth metrics;
- call an LLM or regenerate Creator analysis;
- scan Douyin, download media, enrich evidence, or run ASR/OCR;
- create a Job, queue, scheduler, or background worker;
- optimize Strategy Plans automatically.

## Known limitations

- v1 stores one current Record per Creator iteration; historical Records are
  read-only and selected through the iteration index.
- It records user-entered execution feedback but does not verify publishing or collect platform metrics.
- A Record stays bound to the Pack used at Start; regenerating a Pack does not offer automatic migration.
- CDN redirect allowlisting, Douyin Provider hardening, and standalone Login Plugin host-only Cookie work remain deferred.
